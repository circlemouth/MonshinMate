# 管理画面によるシステム全体セットアップ手順

本書は、P0 セキュリティ変更後の管理者登録・復旧と設定手順です。既定パスワードによるログイン、固定の非常用パスワード、未認証の QR コード取得は廃止されています。

> 本書の標準手順は、隔離コピーと合成データで検証した仕様です。別途承認された本番移行・緊急OTP解除の実績と未検証範囲は [実装履歴](<implementation.md>) を参照してください。以下は承認された作業者向けの手順であり、この文書だけで実環境での実行を許可・指示するものではありません。

## 1. 起動前の準備と既存環境の移行

### バックアップと認証状態

- 既存 DB を削除して初期化しないでください。まず DB と対応する既存の `TOTP_ENC_KEY` を、アクセス制限した別々の保管先にバックアップし、対象バックエンドと復元手順を確認します。稼働中 DB のバックアップは、整合性を確保できる方法を使用してください。
- 管理者の正規の認証状態は、永続化された `admin:account:v1` です。旧 `users` テーブル、`app_settings.admin_password`、`ADMIN_PASSWORD` の値は、新しい管理者アカウントの証明として信頼・自動移行しません。`admin/admin` の初期アカウントも作成しません。
- 今回の運用指定は **パスワードのみ・現在のパスワードを維持**です。移行可能な旧アカウントは後述の **migrate-legacy** を使い、既存ハッシュを継承します。既存パスワード維持のために recovery を実行しないでください。新規環境は **bootstrap**、パスワード紛失等は別承認の **recovery** を使います。患者データやテンプレートは削除しません。
- SQLite では `security_state` テーブル、CouchDB では専用の security DB に認証状態を保存します。CouchDB の既定名は `COUCHDB_DB` に `_security` を付けた名前で、`COUCHDB_SECURITY_DB` で指定できます。運用バックアップにはこの状態も含めてください。通常の設定・問診データのエクスポートには含まれません。
- Firestore 等の非公開アダプターは、永続的な security CAS 機能がないと起動を拒否します。メモリや SQLite への代替保存はしません。基盤固有の対応は [非公開アダプター](<../private/cloud-run-adapter>) で確認します。本書にはデプロイ手順を含めません。

### 鍵と環境設定

- アプリケーションを import／起動する前に、独立した暗号学的乱数の `SECRET_KEY` と、有効な Fernet 鍵である `TOTP_ENC_KEY` を環境へ設定します。固定の既定値や低エントロピーの鍵は本番で拒否されます。
- `K_SERVICE` が存在する環境は、`MONSHINMATE_ENV=local` であっても本番として扱います。鍵の検証は DB 初期化より前です。起動後に秘密情報を読み込めばよい、という順序にはできません。
- ローカル／テスト環境で鍵を省略すると、プロセスごとのランダム値が使われます。再起動・複数ワーカーで認証を維持する実利用では、ローカルでも安定した鍵を設定してください。
- **既存暗号文に対して新しい鍵を無造作に設定し、再暗号化してはいけません。** 既存の鍵と DB を保全してから計画的に移行します。旧 [暗号化スクリプト](<../backend/tools/encrypt_totp_secrets.py>) は、新しい管理者認証状態への移行手段ではありません。
- MFA の秘密値が欠落・復号不能の場合、認証は失敗します。二段階認証の自動無効化や平文へのフォールバックはありません。鍵・DB の整合性を確認し、復旧できない場合は後述の専用 recovery を利用します。

### 現パスワードを変更しない移行

`MONSHINMATE_ADMIN_REQUIRE_MFA=0` をアプリ／移行ツールの両方へ明示すると、MFA未登録アカウントのパスワードのみ認証を許可します。`1` はMFA必須、未指定は従来どおり本番必須／ローカル任意です。その他の値は拒否します。既存のMFA有効・必須登録途中・ロック状態を `0` だけで迂回することはできません。

任意ポリシーで、ログイン済み管理者が再認証後に開始した**新方式の任意TOTP登録**は例外です。確認完了まではパスワードのみログインを維持し、期限切れの任意pendingはログイン時に破棄します。必須登録や由来不明の旧pendingはこの例外にしません。

オフラインの `migrate-legacy` は、旧 `admin` が非初期・有効bcryptハッシュ・MFA無効であり、新しい共有認証状態が未作成の場合だけ使えます。初期資格フラグが不明／true、MFA有効、不正ハッシュ、既存の共有認証状態（空や回復途中を含む）は拒否します。パスワードを再入力・再ハッシュ・変更せずに継承し、新規パスワード用の長さ要件を理由に旧パスワードを変更させません。平文・ハッシュそのものは出力しません。ログインのUTF-8 **72バイト上限は維持**します。旧方式で72バイト超の平文を切り詰めてbcrypt保存していた場合、その長さはハッシュから判別できず、変更なしのログインを保証できません。

承認済み対象には、先に `preflight-legacy --db /absolute/path/to/app.sqlite3 --confirm`（対応するリモートは `--configured-backend`）で読取専用判定ができます。ポリシー `0` を明示し、結果は `eligibility` / `reason` の固定列挙値だけです。SQLiteはread-only SELECT、Firestoreは共有状態と旧adminの最大2文書読取のみで、ハッシュを内部判定しても出力・復号・書込はしません。対応hookのないアダプタは拒否します。成功は予約ではなく、移行時にも再判定とCASを行います。

```bash
# 事前承認された保守作業の例。実行前に対象・鍵・バックアップを確認する。
# 旧管理画面でのパスワード/MFA更新を止め、並行する移行作業を禁止する。
export MONSHINMATE_ADMIN_REQUIRE_MFA=0
venv/bin/python backend/tools/provision_admin.py migrate-legacy \
  --db /absolute/path/to/app.sqlite3 --confirm --acknowledge-password-only
# 対応済みリモートバックエンドは --db の代わりに --configured-backend
```

`--output` は不要です。HTTP／起動時の自動移行、環境変数パスワードへのfallback、共有状態上書きはありません。再実行も拒否されます。移行拒否時はレコードを削除して回避せず、担当者が原因と別手順を確認します。旧DBと共有認証状態の跨ストア原子性は保証しないため、旧管理操作を止めた保守時間帯で行い、移行後は旧管理画面へ戻して資格情報を書き換えないでください。

**実アカウントの移行可否は未確認**です。通常の非初期アカウントを維持するための仕組みであり、どんな旧状態でも変更なしで移せるという保証ではありません。本番切替前に状態確認と合成データでの移行リハーサルが必要です。

## 2. オフラインの初期登録・復旧資格情報を発行する

使用するツールは [provision_admin.py](<../backend/tools/provision_admin.py>) です。旧 [reset_admin_password.py](<../backend/tools/reset_admin_password.py>) は直接リセットを実行せず、新しい手順を案内して終了します。

### 共通条件

1. 対象 DB／バックエンド、鍵、実行権限、バックアップを確認します。ツールは環境ファイルを自動読込しません。必要な環境設定は実行前に管理者が用意します。
2. `bootstrap` または `recovery`、対象指定、`--output`、`--confirm` を明示します。SQLite は **`--db` 必須**です。既定パスへ暗黙に書き込みません。
3. 出力先は、管理者だけがアクセスできるディレクトリの**存在しないファイル**を指定します。ツールは権限 `0600` で排他的に作成し、資格情報を一度だけ書き出します。既存ファイルは上書きしません。秘密値を標準出力・ログ・コマンド引数へ出しません。
4. 資格情報の有効期間は既定 **900 秒（15 分）**です。`--ttl` は **60～3600 秒**を指定できます。DB にはハッシュのみ保存し、一度の使用で失効します。
5. **発行時点で既存の管理者トークンは失効し、アカウントはロックされます。** 資格情報を消費して登録を進めるまで従来のログインはできません。期限切れ・紛失・試行回数超過時はオフラインで再発行します。出力失敗時も状態が更新済みの可能性があるため、状態を確認して再発行してください。

### SQLite の例（仮のパス・実行例）

```bash
# 新規環境: 対象と未作成の出力ファイルを明示
venv/bin/python backend/tools/provision_admin.py bootstrap \
  --db /absolute/path/to/app.sqlite3 \
  --output /private/new-bootstrap-credential.txt --ttl 900 --confirm

# 既存環境の移行・パスワード紛失・Authenticator 喪失
venv/bin/python backend/tools/provision_admin.py recovery \
  --db /absolute/path/to/app.sqlite3 \
  --output /private/new-recovery-credential.txt --ttl 900 --confirm
```

`--db` は、CouchDB または別の永続化バックエンドが設定済みの環境と併用できません。`MONSHINMATE_DB` だけを指定して `--db` を省略することもできません。

### 設定済みリモートバックエンド

CouchDB または対応済みの非公開アダプターでは、正しい接続先・権限を確認して `--db` の代わりに `--configured-backend` を指定します。SQLite でこのオプションを使うことはできません。セキュリティ状態の保存が失敗した場合は処理を拒否し、別バックエンドにフォールバックしません。

### 資格情報の受け渡しと登録

1. 生成した秘密値は承認された安全な経路で対象管理者に渡します。メール本文・チャット・スクリーンショット・共有ログへ貼り付けないでください。
2. ログイン画面の「初期登録」または「専用資格情報でアカウントを復旧」へ進み、対応する資格情報と新しいパスワードを入力します。
3. パスワードは **12 文字以上、UTF-8 で 72 バイト以下**です。日本語などのマルチバイト文字では、文字数が 72 未満でも上限に達します。
4. 明示 `MONSHINMATE_ADMIN_REQUIRE_MFA=0` の新規登録／回復では直接アクセストークンが発行されます。MFA登録が必要な応答では、限定目的の enrollment トークンで QR コードを発行し、Authenticator で読み取ります。**10 分以内**に新しいアプリの 6 桁コードを検証します。登録確認が終わるまで管理 API は利用できません。
5. QR を表示しただけでは有効化されません。QR／秘密値の再読出しはできず、再発行すると以前の pending 登録は使えなくなります。
6. 成功後は不要になった資格情報のファイルを院内の秘密情報廃棄方針に従って処理します。失効済みでも共有保管しないでください。

登録中断後は、設定したパスワードによる `POST /admin/login` が新しい `enrollment_token` を返す契約です。画面で再開できない場合はサーバ管理者に相談し、専用 recovery の再発行でやり直せます。使い終わったオフライン資格情報を再利用することはできません。

## 3. 通常ログインとセキュリティ変更

### 通常ログイン

1. 「管理画面」からパスワードを送信します。MFA 登録済みの場合、認証チャレンジが発行されます。
2. **5 分以内**に Authenticator の 6 桁コードを入力します。パスワード確認に結び付いたチャレンジが必要で、コードだけではログインできません。
3. 成功すると **15 分**の管理者アクセストークンが発行されます。目的は `access`、audience は `monshinmate-admin`、scope は `admin push:manage` です。期限切れや失効時には再ログインします。
4. 同じ 30 秒枠の TOTP は、登録・ログイン・再認証をまたいで再利用できません。直前に認証した場合は、**次のコードに変わるまで最大約 30 秒待って**操作してください。

今回指定の `MONSHINMATE_ADMIN_REQUIRE_MFA=0` では、MFA未登録かつ必須登録途中でないアカウントはパスワードだけでログインできます。本番で未指定、または `1` ならMFA必須で、未登録時は登録用トークンしか発行されません。既存MFA有効アカウントには、任意ポリシーでも6桁コードが必要です。

### パスワード変更・Authenticator 再登録

- 「セキュリティ」で現在のパスワードと新しい TOTP コードにより再認証します。再認証トークンは **5 分**有効で、そのときのアクセストークンに結び付きます。
- パスワード変更後も MFA は維持されます。旧アクセストークン／チャレンジは失効するため、新しいパスワードでログインし直します。
- Authenticator 再登録では、確認前は既存の MFA 秘密値が有効です。pending 登録は 10 分有効ですが、ログイン済み管理者の確認には 5 分以内の再認証も必要です。画面の案内に従い **5 分以内**に確認してください。
- 新しいコードの確認成功時にだけ秘密値を切り替え、古いトークンを失効させます。新しいアクセス資格情報で操作を続けます。
- MFA必須ポリシーでは無効化を拒否します。任意ポリシーでの無効化にもアクセストークンと直近の再認証（MFA有効時はTOTPを含む）が必要です。

### API 契約一覧

| 操作 | 入力・認証 | 結果 |
| --- | --- | --- |
| `POST /admin/login` | `password` | `totp_required` と `challenge_token`、または `enrollment_required` と `enrollment_token`。MFA任意・未登録かつ登録途中でない場合は直接アクセス可 |
| `POST /admin/login/totp` | `challenge_token`, `totp_code` | 一回限りのチャレンジを消費してアクセス発行 |
| `POST /admin/bootstrap`, `POST /admin/recovery` | `credential`, `new_password` | 一回限りの資格情報を消費。明示MFA任意ならaccess、それ以外は10分のenrollmentトークン発行 |
| `POST /admin/totp/setup`, `POST /admin/totp/regenerate` | enrollment Bearer、または access Bearer + `X-Admin-Reauth` | `enrollment_id`, `provisioning_uri`, `qr_code_data_url`, `expires_in`。生成した秘密値のみ一度提示 |
| `POST /admin/totp/verify` | 同じ登録所有者の認証、`enrollment_id`, `totp_code` | pending 登録を有効化してアクセス発行 |
| `POST /admin/reauth` | access Bearer、`password`, `totp_code` | 5 分の `reauth_token` |
| `POST /admin/password/change` | access Bearer + `X-Admin-Reauth`、`current_password`, `new_password` | MFA 維持、旧トークン失効 |
| `POST /admin/totp/disable` | access Bearer + `X-Admin-Reauth` | MFA必須policyは `403`。明示policy `0` は無効化と旧token失効 |
| `GET /admin/auth/status` | access Bearer は任意 | 秘密値を含まない認証状態 |
| `GET /admin/totp/mode` | access Bearer | 現在のモード |

次の旧経路は **HTTP 410** を返します: `POST /admin/password`、`POST /admin/password/reset/request`、`POST /admin/password/reset/confirm`、`POST /admin/password/reset/emergency`、`GET /admin/totp/setup`、`PUT /admin/totp/mode`。固定の `ADMIN_EMERGENCY_RESET_PASSWORD` は復旧資格情報として使用しません。認証失敗を繰り返すと試行上限／永続的なレート制限により拒否されます。

## 4. 表示・テンプレートの設定

1. 管理画面の「外観・通知設定」で表示名、メッセージ、テーマカラー、ロゴを設定します。自動保存の完了を確認してください。
2. 「テンプレート」で初診・再診のテンプレートを作成し、質問文、補足、入力方法、必須条件、条件表示を設定します。
3. プレビューで患者画面の表示を確認します。追質問やサマリーを使用する場合は、テンプレート側と LLM 側の両方で必要な設定を行います。
4. ロゴ・項目画像は **PNG／JPEG／WebP の単一フレームのラスター画像**に限ります。入力・再エンコード後とも **512 KiB 以下**、**4,000,000 ピクセル以下**が上限です。SVG／HTML／アニメーション画像は使用できません。メタデータは除去して再エンコードされます。

## 5. LLM 設定

1. 「LLM設定」で、利用可能なプロバイダー、モデル、接続先を選択します。設定・モデル一覧・疎通テスト・詳細状態の取得は管理者認証が必要です。
2. API キーの入力は変更時に行います。保存済み秘密値は API 応答やエクスポートから再取得できず、設定済みかどうかのみ確認できます。既存キーを取得するためにログや DB を共有しないでください。
3. 接続先はサーバ管理者が許可した範囲で指定します。任意の内部 URL や資格情報入り URL は使用せず、検証を無効化してエラーを回避しないでください。
4. モデル一覧取得／疎通テストは合成データで行います。Google 系など非公開アダプター固有の認証・可用性は [非公開アダプター](<../private/cloud-run-adapter>) 側で確認し、サービスアカウントの JSON 秘密鍵を管理画面へ入力しません。
5. 設定保存を理由に、過去の問診データを LLM へ自動再送しません。設定変更後の確認は新しい合成セッションで行います。
6. LLM の不調時も、患者画面は可能な範囲で既定質問にフォールバックします。詳細な接続状態は管理者画面で確認してください。

## 6. バックアップ・インポートと動作確認

- 設定と問診結果のエクスポートは管理者だけが利用できます。秘密鍵、管理者認証状態、患者セッションの capability、LLM の秘密情報はポータブルデータに含みません。移行先では管理者登録・秘密情報設定を別途行います。
- インポートは検証後に一括で反映できる **atomic import hook** が必要です。未対応のバックエンドは **HTTP 501** で拒否し、一件ずつ部分的に書き込む代替処理は行いません。CouchDB／Firestore 等の可否もアダプターの対応状況に依存します。未対応時に DB を削除してやり直さないでください。
- インポートの上限は 5 MiB、レコード数は原則 100 件です。暗号化済みでも上限・構造検証を回避しません。画像には前節の制限も適用されます。
- 動作確認は、隔離環境の合成患者で新規問診を開始し、回答・確定・管理者による結果表示と認証付きダウンロードを確認します。保存済みの実患者データを試験に流用しません。
- 本変更で実施した検証範囲と基盤ごとの未検証事項は、[実装記録](<implementation.md>) を参照してください。

## 7. 監査と障害時の確認

- 新しい認証処理は `security` logger に `admin_security_event` とイベント名・認証バージョンを記録します。例: `offline_credential_issued`、`offline_credential_consumed`、`totp_enrollment_started`、`totp_enrollment_completed`、`password_changed`、`totp_disabled`。
- 秘密値、QR 内容、パスワード、JWT、資格情報そのものは記録しません。認証情報を含むリクエスト本文を別のロギング層で出力しないようにも注意してください。
- アプリ側のファイルログ設定と保管・ローテーションを確認してください。オフライン CLI はアプリのログ初期化を行わないため、イベントが標準エラーへ出る場合があります。旧 `audit_logs` テーブルと新イベントが常に二重記録されるとは限りません。
- `401` は未認証・失効・期限切れなど、`403` はMFA必須等のポリシー違反、`429` はレート制限、認証状態の保存障害や MFA 復号不能の `503` は管理者による調査が必要です。エラーを理由に MFA や永続化検証を迂回しないでください。

日常操作は [管理画面の使い方](<../docs/admin_user_manual.md>)、構成の一次情報は [システム概要](<system_overview.md>) を参照してください。
