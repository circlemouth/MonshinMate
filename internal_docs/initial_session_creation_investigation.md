# 初診のセッション作成失敗：コード・隔離検証による調査

## 範囲と結論

- 対象症状：初診の基本情報を入力し、「受診種別を選び直す」ボタンと「次へ」がある画面で「次へ」を押すと、セッション作成失敗の通知が出る。
- 作業ブランチ：`investigate/initial-session-creation`。
- **本番の現行初診フローを失敗させる不整合を確認**：既定問診「形成外科・美容皮膚科」の初診テンプレートには `personal_info` がなく、UIが必ず送る `answers.personal_info` と不一致。現在の作成ハンドラーはこの回答を HTTP 422 / `unknown answer item` で拒否する。SQLiteとfake Firestoreでも同条件を再現した。
- 初期のローカル調査後、ユーザーが本番revision、失敗ログの安全なmetadata、公開テンプレートの読み取りを明示許可。**2026-10-13の日本時間午前には、正確な `POST /sessions` パスの失敗12件すべてでHTTP 422を確認**した。稼働revision/digestは配備履歴と一致。患者本文を取得していないため、個々の過去リクエストの入力と422応答本文までは照合していない。
- アプリ実装、テンプレート、患者データ、認証状態、秘密値、デプロイを変更していない。調査文書だけを追加する。非公開サブモジュールの取得・更新も行わない。

## 処理の追跡

1. [基本情報画面](<../frontend/src/pages/BasicInfo.tsx#L212-L263>) は初診で必ず `answers.personal_info` を送信する。`/sessions` の非2xx応答、JSON解析失敗、患者資格情報の保存検証失敗を、すべて同じ汎用エラー通知へまとめる。通知だけでは入力・設定不整合、DB障害、通信障害を区別できない。
2. [API公開境界](<../backend/app/api_policy.py#L50-L70>) と [作成レート制限](<../backend/app/patient_security.py#L36-L59>) は匿名作成を許可するが、IP別・全体の永続レート制限を先に実行する。ここで429や503になる別経路も存在する。
3. [作成ハンドラー](<../backend/app/main.py#L3444-L3481>) は既定テンプレートIDを設定から取得し、当該IDの初診テンプレート、`default` の初診テンプレートの順に使う。保存済みテンプレートが見つかると、基本情報項目が欠けていても補完しない。両方ない場合のハードコードfallbackも主訴・発症時期のみで `personal_info` を含まない。
4. 同ハンドラーの性別フィルタは `gender_enabled` を参照せず `gender` の値で除外するため、`personal_info` に性別条件が残る場合も不一致が生じ得る。
5. [回答バリデータ](<../backend/app/validator.py#L61-L68>) は未知の項目IDを422で拒否する。したがって今回の候補は臨床セッション保存・患者token発行より前に失敗する（永続レートカウンタの更新は別）。任意の未知回答を許可するよう緩めるべきではない。
6. [起動時のテンプレート投入](<../backend/app/main.py#L1006-L1024>) は未作成時のみ。[現在の初診既定項目](<../backend/app/main.py#L598-L608>) が正しくても、旧保存済みテンプレートは再起動だけでは修復されない。
7. [管理画面](<../frontend/src/pages/AdminTemplates.tsx#L231-L285>) は基本情報項目を編集一覧から隠し、保存時に元の項目だけを復元する。欠損していた項目を自動追加しないため、管理画面での単なる再保存も修復保証にならない。
8. [Firestore保存](<../private/cloud-run-adapter/monshinmate_cloud/firestore_adapter.py#L801-L825>) は初回保存時のcapability未作成を明示許可しており、「token発行前に保存するから必ず409になる」という説明は成立しない。実SDK通信・IAM・本番競合は別途未確認。

## 承認後の本番読み取り結果（2026-10-13）

- ユーザーの「今日の午前」を日本時間として、2026-10-13 00:00〜12:00 JST（2026-10-12 15:00〜2026-10-13 03:00 UTC）を照合。公開設定のtimezoneも `Asia/Tokyo` だった。
- 既存のCloud Run requestログを、時刻、POST、URL末尾 `/sessions$` に限定し、status/時刻/revision等のmetadataだけを取得。**16件中200が4件、422が12件**。同じ条件のfrontend失敗も422。失敗は07:48:28 JSTに1件、09:02:18〜09:04:33 JSTに11件。対象期間・経路に429や5xxは観測しなかった。最初の広めのURL正規表現は子APIも含み得るため、件数は末尾一致で再確認した16件だけを使用する。
- frontend/backendのcanonicalと全既存tagはそれぞれ配備記録の固定revisionを指し、digestも一致。秘密値や環境変数の全体は読まず、name/URL/traffic/revision/digestのみを照合した。
- 公開bootstrapが返す既定問診は「形成外科・美容皮膚科」。frontendと、その既存backend転送先の両方で一致。同問診の初診テンプレートには、ネスト項目を含め20項目あるが、`id=personal_info` も `type=personal_info` もない。一方、`default` の初診には正しい `personal_info` がある。
- 作成APIは選択されたカスタムテンプレート自体が存在するとdefaultへ切り替えない。そのため、defaultに正常な基本情報項目があることでは、カスタム初診の不一致を救済できない。
- 公開GET以外の患者API呼び出しは実施しない。Firestore/患者セッションDB、入力本文、token、秘密値は閲覧せず、本番への合成セッション作成も行っていない。
- 結論：**現行本番設定と配備済みコードには、正しい初診入力でも422を返す確定的な不整合がある。午前の失敗ステータスも一致する。** ただし、当該利用者の各過去リクエストの応答本文を `unknown answer item` として直接観測したわけではなく、個別422の全原因やテンプレート変更の時刻・変更者までは確定していない。

## 隔離再現

本番データ・環境ファイル・ADC・秘密情報はコピーせず、ソース専用ランナーの一時コピー、合成SQLite、合成キー、ネットワーク禁止のfake Firestoreを使用した。追加の診断テストは一時コピーにのみ配置し、実リポジトリのテストや実装は変更しない。

| 合成条件 | SQLite | fake Firestore | セッション保存・token発行 |
| --- | --- | --- | --- |
| 初診テンプレートに `personal_info` なし | 422 `unknown answer item` | 同左 | 未到達 |
| 初診テンプレートに正しい `personal_info` あり | 200 | 200 | 成功 |
| 基本情報項目IDが `patient_basic_info` | 422 `unknown answer item` | 同左 | 未到達 |
| 基本情報項目が性別フィルタで除外 | 422 `unknown answer item` | 同左 | 未到達 |
| 選択/defaultテンプレートとも欠落 | 422 `unknown answer item` | 同左 | 未到達 |
| 再診・基本情報回答なし | 200 | 200 | 成功 |

追加でSQLiteに古い初診defaultを保存して起動イベントを実行した。項目構成は変更されず、その後の初診作成は同じ422になった。

- バックエンド既存対象試験：**22 passed**。
- 非公開Firestore既存対象試験：**20 passed**。
- 調査用matrixと既存テンプレート起動検証：**13 passed**（現在の失敗条件を期待値にした診断試験。修正完了を意味しない）。
- 全実行の終了コード0、各5件の非推奨警告。
- 配備履歴に記載されたbackendソース `177543e` と現HEADの [main.py](<../backend/app/main.py>) / [validator.py](<../backend/app/validator.py>) / [patient_security.py](<../backend/app/patient_security.py>) / [patientSession.ts](<../frontend/src/utils/patientSession.ts>) に差分なし。[BasicInfo.tsx](<../frontend/src/pages/BasicInfo.tsx>) の差分は無効日付判定の型修正のみで、送信・通知処理は同一。承認後に本番revision/digestと配備記録の一致も確認した。
- フロントテスト・build・型検査、ブラウザE2E、実Firestore/実SDKの書き込み・並行処理試験は今回未実施。Cloud Runは上記の限定的な本番読み取りのみで、患者フローの実サービス検証ではない。実装変更がないため、全体回帰も未実施。

## 残る観測の限界

- 過去の失敗リクエストについて、応答本文と当該利用者の個別操作との直接対応は未確認。患者入力やtokenを使った照合は不要であり行わない。
- テンプレート欠損の作成時期・変更者は今回の許可範囲外で調べていない。現行の不整合と、午前の422という事実を区別する。
- 別の日・経路で503/500/429や200応答契約不一致が生じた可能性まで否定するものではない。
- 本番への合成セッションPOSTも書き込みを伴うため、この読み取り許可に含めず別承認とする。時間待ちや連続再試行で422の設定不整合は直らず、作成レート制限に達する可能性もある。

## 修正方針（未実施）

- 第一候補：固定UIの基本情報は初診作成の専用サーバー契約として検証・正規化し、カスタム/旧テンプレートの項目有無に依存させない。その他の未知回答ID・サイズ制限は厳格に維持する。
- 必要に応じてテンプレート解決/fallback/性別条件の扱いを患者表示・作成・復元で整合させる。保存済み問診や認証状態は自動的に書き換えない。
- エラー通知は422・429・一時障害等を区別し、患者本文や生のproviderエラーを表示・ログへ出さない。
- テンプレート初期化・削除・DB初期化を障害回避策にしない。既存質問・プロンプトを失う危険がある。
- 本番反映前には原因確定、修正回帰、合成患者フローの隔離確認、必要な実SDK/検証環境確認、運用・デプロイの別途承認が必要。
