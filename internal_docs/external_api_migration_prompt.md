# 外部接続サービス保守担当者向け：MonshinMate API移行の実装プロンプト

以下を接続サービスのリポジトリで作業する担当者／コーディングエージェントへ渡してください。

---

あなたは、このリポジトリから MonshinMate（問診メイト）へ接続する実装の保守担当者です。MonshinMate 側のセキュリティ改修に合わせ、**影響調査だけで終わらず、該当する接続コード・型・設定例・テスト・運用文書を修正し、内部テストまで完了**してください。

## 0. 作業境界・正本

- MonshinMate の対象コードは公開リポジトリの `release/password-only-admin-update`、APIアプリ版 `177543e`（ビルド時の非公開アダプタ参照 `33e5c5e`、追加の運用者手順は `569bd09`）です。**本番は保守中で、切替完了前**です。追加承認を受け、バックアップ・復元確認後にOTPだけを解除し、通常移行手順で既存パスワードの保持を確認しました。現在frontendのログインURL再読込を修正・再buildしています。このプロンプトだけを本番移行完了通知として扱わず、承認済み配備revisionの連絡を別途確認してください。接続側の作業はコード修正と隔離内部検証までです。
- 本番アクセス、実患者での試験、デプロイ、鍵取得・交換、Secret Manager／IAM／DB変更、管理者初期登録・回復は実施しないでください。
- 実環境ファイル・認証情報・患者データ・監査ログを調査／テスト入力にしないでください。テストは合成患者・合成キーと mock／承認済み使い捨て環境だけを使います。
- 作業ブランチを分け、既存の未コミット変更を保持してください。無関係なリファクタリングは避けます。
- 正本は MonshinMate の [API仕様](../docs/session_api.md)、[認可ポリシー](../backend/app/api_policy.py)、[セキュリティ報告](security_review.md) です。別リポジトリへ渡す場合、これらの**承認された対象版**を併せて参照できるようにしてください。参照できない箇所を推測で補わず、不足事項を報告してください。
- ホスト名や配置固有の `/api` prefix を推測で変更しないでください。以下は API の論理パスです。既存の承認済み base URL／proxy 契約に従って組み立てます。

## 1. 最初に呼出箇所を棚卸しする

APIクライアント、型定義、サーバー側連携、ブラウザコード、定期実行、エクスポート／ダウンロード、再送キュー、ログ／APM、設定例、CI を調べ、次の表を作ってください。

`呼出箇所 | method/path | 用途 | 現在の認証 | 必要な変更 | 対応テスト`

用途は「サマリー連携」「患者問診」「管理操作」「明示公開API」に分けます。**利用していない用途の認証フローを新規実装しないでください。** 特にサマリー連携だけのサービスに管理者 MFA や患者トークンは不要です。既に正しく専用キーを送っている場合、不要な認証変更ではなく契約・エラー処理の回帰テストを追加します。

## 2. 認証は3種類を完全に分離する

| 用途 | 必須の資格情報 | 禁止する代替 |
| --- | --- | --- |
| サマリー連携3 API | `X-MonshinMate-Api-Key: <専用連携キー>` | 管理JWT、患者トークン、固定管理パスワード |
| 患者セッション更新 | `Authorization: Bearer <session_token>` | UUIDだけ、管理JWT、連携キー |
| 管理操作 | `Authorization: Bearer <admin_access_jwt>` | 患者トークン、連携キー、旧固定パスワード |

資格情報は宛先・用途別クライアントへ限定して付けてください。共通HTTPクライアントがすべての宛先へ資格情報を付ける実装や、認証失敗時に別種のキーを試すフォールバックは禁止です。別originへのredirectへ認証ヘッダーを転送しないでください。

秘密を URL、クエリ、HTML、フロントエンド配布物、ログ、エラー、APMへ載せません。サマリー専用キーは接続サービスの信頼されたサーバー側で保持し、ブラウザへ配布しません。ブラウザ連携が必要なら、自サービスの認証・認可を伴うサーバー中継を使い、無認証の代理取得口を作らないでください。

## 3. サマリー連携を利用している場合

3 APIすべてに専用キーを付けます。既存キーをこの作業で読み出したり変更したりせず、設定の参照経路と合成値によるテストを修正してください。

1. `POST /patient-summary`
   - JSON：`{ "patient_name": "合成患者", "dob": "2000-01-01" }`
   - 成功は JSON。`session_id`, `patient_name`, `dob`, `visit_type`, `questionnaire_id`, `finalized_at`, **`markdown`** を返します。本文そのものが Markdown とは解釈しません。
   - 氏名・生年月日の完全一致に基づく最新の**確定済み**問診です。該当なしは404。部分一致検索や未確定情報取得へ変更しないでください。
2. `POST /patient-summaries`
   - JSON：上記患者情報に `cursor`（初回 `null`）と `limit`（1〜100、既定20）を指定。
   - `items` と `next_cursor` を処理。該当なしは `items=[]`, `next_cursor=null` であり404ではありません。
   - cursor は返された不透明値をそのまま次へ渡し、解析・組立・患者をまたぐ再利用をしません。不正cursorは400。
   - 各itemは医療情報・個人情報を含み得ます。全件のログ出力や不要なキャッシュを禁止します。
3. `POST /patient-summary/pdf`
   - JSON：`patient_name`, `dob`, `session_id`。
   - 成功は `application/pdf` のバイナリ。JSONとして処理しません。
   - 指定患者が所有する**確定済み初診**のみ取得可。対象なし・所有者不一致・再診・未確定はすべて404です。UUIDから別患者の情報を取得しようとしません。
   - エラーボディをPDFとして保存せず、必要な認証付き要求と成功ステータスを確認します。

`/system/patient-summary-api` は管理側の設定確認用途です。キーを公開APIから登録・更新する仕組みを実装せず、クライアント起動時の無認証診断にも使わないでください。

## 4. 患者問診を扱っている場合だけ実装する

- `POST /sessions` の応答は `status:"created"`, `id`, `session_token`, `expires_at`, `answers`。トークンを UUID と分離して現在患者の状態に保持します。有効期間は発行から24時間です。
- 次のPOSTすべてに、そのセッションの患者Bearerを付けます。
  - `/sessions/{id}/answers`
  - `/sessions/{id}/llm-questions`
  - `/sessions/{id}/llm-answers`
  - `/sessions/{id}/llm-answers/batch`
  - `/sessions/{id}/finalize`
- 質問IDは取得・発行されたものだけを送ります。未知の質問や勝手に生成した `llm_*` を送らず、質問種別の型・必須条件を守ります。
- 通常本文256KiB、回答の深さ6・文字列4000文字・辞書200項目・キー128文字・配列100項目の上限を考慮します。サーバー検証を省略できるとは考えません。
- 旧UUIDだけのローカルセッションは再開不可。紛失／期限切れトークンをUUIDから再発行するAPIはありません。適切に旧状態を消去し、必要なら利用者へ新規開始を案内します。患者作成は冪等ではないため、応答不明時に無制限の自動再作成をしません。
- finalize は**同期**です。成功応答は `{id,status:"finalized",finalized_at}` の受付情報だけ。旧レスポンスの回答・氏名・要約を参照する型や完了画面を修正します。
- 応答が失われた場合、同じ有効トークンで finalize を明示的に再試行できます。確定済みなら受付情報を再取得し、再生成・回答の上書きはしません。finalize を一般的なオフライン自動再送キューへ入れません。
- 確定後の更新は409です。上書き成功として扱いません。
- 完了／中止／アイドル／患者切替で回答、トークン、再送キューを消去します。要求・再送を患者ID＋トークン＋画面世代に結び付け、遅延応答が次患者の状態を更新しないようにします。

## 5. 管理APIを呼んでいる場合だけ実装する

設定、診断、メトリクス、管理データ、各形式のダウンロード、画像登録等は原則管理JWTが必要です。公開かどうかを画面やパス名で推測せず、正本の許可リストで判定します。

- `POST /admin/login` に `{password}` を送信。今回の運用指定はパスワードのみです。`status:"ok"` と `access_token` を受け取った場合は直接ログイン完了（有効900秒）とします。HTTP成功だけでは判定せず、以下のchallenge／enrollment応答とは区別します。
- `totp_required` なら、300秒の `challenge_token` を使って `POST /admin/login/totp` に `{challenge_token,totp_code}` を送信し、有効900秒のアクセストークンを取得します。
- `enrollment_required` と登録用トークン（600秒）は用途限定の手続きです。通常の管理JWTとして使わず、正本の登録フローへ案内します。
- MFAの必須／任意は `GET /admin/auth/status` の `mfa_required`、アカウントの登録状態は `is_totp_enabled` を参照します。任意でも登録済みアカウントのOTPを省略しません。bootstrap/recoveryも、直接accessとenrollmentの両応答を区別します。
- 重要操作は `POST /admin/reauth` へ管理Bearer＋`{password}`（MFA有効アカウントだけ `totp_code` も必要）を送り、得られる `reauth_token` を `X-Admin-Reauth` に付けます。有効300秒で現在のJWTに結び付き、ログイン世代をまたいで再利用できません。
- `POST /admin/password/change` は管理Bearer＋再認証と `{current_password,new_password}`。変更後は旧JWTが失効するためローカル認証状態も破棄します。
- refresh token や自動無人MFAのAPIがあるとは仮定しません。期限切れや失効時は再ログインへ戻します。同じTOTPの再利用を繰り返して突破しようとしません。
- 旧init/reset/emergency、`GET /admin/totp/setup`、旧mode変更等の410経路を削除します。固定初期／非常用パスワードやMFA無効化へフォールバックしません。
- bootstrap/recoveryと既存パスワード継承（`migrate-legacy`）は運用者の別承認によるオフライン手続きです。現在のパスワードを維持するためにクライアント側から再設定を要求したり、連携サービスが資格情報を自動発行したりしません。
- 管理画面のダウンロードは認証fetch→Blob等へ修正し、logout／画面離脱後の遅延body・保存・表示を世代検証とabortで止めます。Blob URLは利用後に破棄します。

**サマリー3 API以外の管理操作を無人連携が必要としている場合、管理者のパスワードやTOTP秘密鍵を埋め込んで自動化しないでください。** 現行契約では目的別M2M権限が未定義であることを報告し、MonshinMate側と別途設計・承認するまでその機能の切替を保留します。

## 6. エラー・再送・保存を修正する

- 400／422：入力・型・cursor・質問IDを見直す。無限再送しない。
- 401：対象用途の資格情報を確認。別用途の資格情報や旧認証で再試行しない。
- 403：権限不足等として停止。クライアントだけで回避しない。
- 404：各APIの定義に従って対象なしを表示。他患者の存在を推測しない。
- 409：確定済み／同時操作等。上書きや無制限の即時再試行をせず状態を説明する。
- 410：廃止経路。旧APIへ戻らず呼出箇所を修正する。
- 413：本文サイズ超過。データを勝手に欠落させて成功扱いにしない。
- 429：`Retry-After` があれば尊重し、回数・時間を制限したbackoffを使う。
- 503／通信不明：共有状態障害等としてfail-closed。成功扱いせず、操作の冪等性・副作用を確認してから限定的に再試行する。LLMや作成を無条件に再実行しない。
- 501：特にFirestore／CouchDBの未対応一括インポート。成功・部分成功と表示せず、無断で個別書込に分解しない。

レート上限は共有です。サマリー連携30/IP/分・300全体/分、患者作成60/IP/分・300全体/分、LLM10/セッション/分・120全体/分を考慮してください。一般のPOST全体に無条件の自動retryを設定しません。

患者氏名、生年月日、回答、要約、PDF、認証ヘッダーをデバッグ出力・トレース・例外・失敗スナップショットへ残さないでください。`no-store` を尊重し、業務上必要な保存以外の共有キャッシュを避けます。

## 7. 必須の受入テスト

該当する用途について、mock／合成データで次を自動テストしてください。

- 正しい認証ヘッダーが正しいAPI・宛先だけに付く。欠落／無効／用途違いの資格情報は拒否され、旧方式へのfallbackがない。
- サマリー：JSONの `markdown`、一覧の空結果／全ページ／不正cursor、PDFのMIMEとバイナリ、患者不一致・未確定・再診の404、401／429／503。
- 患者：作成→トークン付き回答→確定→receipt再取得、別患者トークン／期限切れ／旧UUIDの拒否、確定後409、完了消去、患者切替後の遅延応答と再送拒否。
- 管理：パスワードのみ→JWT、MFA有効時のpassword→challenge→TOTP→JWT、bootstrap/recoveryの直接access／enrollment分岐、challengeとJWTの区別、失効／期限切れ、再認証の付与と世代拘束、logout後のJSON／Blob副作用拒否、410経路の不使用。
- サイズ／検証エラー、503を成功扱いしないこと、retry上限、機密値を含む合成エラーがログへ出ないこと。
- 型検査、既存単体／統合テスト、ビルド。既存失敗と今回の新規失敗を区別し、mockだけの検証を実サービス疎通と呼ばない。

## 8. 納品と停止条件

1. 呼出箇所の棚卸し表と、該当／非該当の根拠。
2. 実際の修正、追加テスト、秘密値を含まない設定例、移行文書。
3. 実行した検証コマンド・結果・未検証項目。対応不要だった箇所にも根拠を付ける。
4. 必要な接続先・連携キーの参照名・運用者への依頼事項（値は不要）。
5. MonshinMate側と合わせた将来の切替順序、対象revision、ステージング検証、保守時間帯、安全な切戻し条件。旧患者UUIDセッションは持ち越さない。旧無認証APIや固定パスワードを再公開するrollbackは禁止。

MonshinMate の Cloud Run アダプタにはローカル互換修正が入っていますが、実クラウド／並行DB／配布revisionの確認は別ゲートです。このサービス側だけの成功をもって本番移行可能とは判定しないでください。

**コード修正と隔離内部テストを完了したところで停止し、本番反映は行わないでください。**
