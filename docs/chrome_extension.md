# Chrome拡張の問診メイト連携

## 院内運用の構成

院内運用では、`medical-document-creator-extension`に統合した「患者情報」の「問診」タブを使用する。
従来の`extensions/patient-summary`は互換性確認用に残し、新規配布の対象としない。

統合拡張はCLINICSの患者番号、氏名、生年月日、性別を、合意済みのDOM識別子から読み取る。
問診検索には氏名と生年月日を使い、`POST /patient-summaries`で完全一致する確定済み履歴だけを取得する。
XPathの手動設定は使用しない。

## 表示

CLINICSの表示患者が変わると、拡張は問診履歴を自動取得する。
履歴は新しい順で表示し、最新件だけを初期状態で開く。
利用者は「更新」で再取得できる。

ページングは`next_cursor`がなくなるまで続ける。
Markdown本文の累計が25MBを超える場合は、新しい問診だけをメモリに保持し、古い問診の省略件数を警告する。
問診内のHTMLは実行せず、テキストとして表示する。

KaruLog検索から手動選択した患者の問診も表示できる。
この場合は表示だけとし、CLINICSへの登録を無効にする。

## CLINICSへの登録

登録できるのは、CLINICSで現在表示している患者の最新問診だけである。
確認画面で、患者、基本情報の差分、表示中カルテ、初診PDFを確認し、各工程を個別に選択する。

基本情報は、問診値が空でないカナ、郵便番号、住所、電話番号だけを更新する。
氏名、生年月日、性別は照合に使うが、問診値で更新しない。
郵便番号辞書で住所を分解できない場合は、都道府県と市区町村を空にし、住所全文を住所欄へ保存する。

カルテ本文は、当日の診療中で、画面上で一意に特定できる表示中カルテだけへ追記する。
保存直前にカルテを再取得し、既存本文と問診Markdownを2つの改行で連結する。
診療行為と既存HTMLを保持し、保存後に版、本文、診療行為を再取得して検証する。
同じ問診本文が既に含まれる場合は追記しない。

初診PDFは`POST /patient-summary/pdf`で取得し、CLINICSの患者書類へ新規追加する。
ファイル名は`問診票_初診_YYYYMMDD_<session-short>.pdf`とし、患者氏名を含めない。
明示的な別実行は新規書類として追加する。
同一実行中の応答不明では、書類一覧を再読込して二重登録を防ぐ。

工程は患者基本情報、カルテ、PDFの順に直列実行する。
いずれかが失敗した場合は後続工程を実行せず、各工程の結果を表示する。

## 認証とビルド

問診メイトの送信先は`https://monshinmate.maruguchi-clinic.com`に固定する。
院内配布用ビルドは、権限600の`/home/hayato/.local/share/clinic-hermes/home/monshinmate-mcp.env`から`MONSHINMATE_CLINIC_HERMES_API_KEY`を読み込む。
読み込んだキーはビルド時定数とし、Chrome storage、設定UI、ログに保存しない。

実キーを含む配布物は平文相当の資格情報を含むと扱う。
管理対象の院内端末だけへ配布し、キーのrotation後はCloud Runの再デプロイと拡張の再ビルド・再配布を行う。

## 障害時の確認

- 401または403: Secret Managerのキーと拡張ビルドに埋め込んだキーが一致しているか確認する。
- 429: 短時間の呼出し集中を解消し、時間を空けて「更新」を実行する。
- 問診なし: 氏名と生年月日が完全一致し、対象問診が`completion_status='finalized'`か確認する。
- PDFなし: 対象が初診かつ確定済みで、指定患者に所有されているか確認する。
- CLINICS登録停止: 患者同一性、当日の診療中状態、表示中カルテの一意性、保存版を確認する。
